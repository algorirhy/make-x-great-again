# 延迟自动 X 拉黑：需求、设计与使用说明

## 文档定位

本文档是 `codex/delayed-auto-block` 个人开发分支的功能说明，也是后续维护时的需求
基线。它不是上游项目当前商店版本的官方说明。

- 使用范围：个人侧载的 Chrome / Chromium 扩展；
- 功能状态：已实现，默认关闭；
- 暂不支持：Firefox、Safari、Chrome Web Store 发布；
- 数据原则：队列和处理结果保存在本机，X 原生拉黑结果保存在 X 服务端。

主 README 只保留功能入口和推荐配置；完整需求、技术边界、迁移和验证步骤都维护在
本文档，避免把个人分支的大量细节混进上游通用文档。

## 需求背景

原项目已经支持三种动作：本地隐藏、X 静音和 X 拉黑，但它们各有不同问题：

1. **本地隐藏不能跨设备。** 已隐藏账号在当前扩展中不可见，但手机端、其他浏览器
   或未安装该扩展的环境仍能看到。
2. **即时自动拉黑可能产生集中的 X 请求。** 原项目的自动类别如果直接配置为
   “X 拉黑”，命中后会走原有的前台动作队列；垃圾账号密集时仍可能在较短时间内
   请求很多次，存在 X 风控风险。
3. **已有历史记录需要补处理。** 过去已经积累了一批本地隐藏账号，不能只处理功能
   上线后的新命中。

因此采用两阶段方案：先用本地隐藏立即清理页面，再把符合条件的记录交给更慢的
持久队列，使用当前登录的 X 会话逐个执行 X 原生拉黑。

```text
新垃圾账号命中或读取到历史本地隐藏记录
→ 立即保持/执行本地隐藏
→ 建立“待 X 拉黑”状态
→ 在账号匹配的已登录 X 页面中限速逐个处理
→ 成功后保存“已 X 拉黑”，在手机和其他设备上生效
```

## 已确认的需求

### 必须实现

- 延迟拉黑使用独立开关，默认关闭；
- 新命中先立即本地隐藏，不等待 X 请求；
- 历史本地处理记录可以建立延迟队列；
- 使用现有 `performXAction()`，始终一次一个，不并发；
- 数字 userId 优先，缺失时使用合法 handle 兜底；
- 保存成功、等待重试、失败和目标不可用等状态，避免已确认成功的目标重复提交；
- 401、403、429 必须熔断或冷却，临时错误有限次重试；
- 任务只在当前已登录且账号匹配的 X 页面中运行；
- 设置页展示整体统计，处理记录展示每个账号的 X 状态；
- 关闭开关只暂停，不删除队列和成功记录。

### 明确不做

- 不开发 JSON / CSV 图形化导入页面；
- 不开发复选框、批量选择和“拉黑选中账号”按钮；
- 不把 X 静音自动升级成拉黑；
- 不在拉黑前额外查询 X 拉黑列表或目标状态；
- 不在浏览器和 X 页面全部关闭后继续运行；
- 不保证 exactly-once，也不承诺任何限速能规避 X 风控；
- 不自动解除 X 静音或拉黑。

## 推荐使用方式

如果目的是避免原项目即时自动拉黑的请求过于集中，推荐这样配置：

1. 将需要处理的自动类别设为“本地隐藏”；
2. 开启“延迟自动 X 拉黑”；
3. 保持一个已登录且与绑定账号一致的 X 页面打开；
4. 不要同时为大量类别配置即时“X 拉黑”。

这套组合会立即隐藏垃圾内容，同时把 X 原生动作均匀分散。延迟功能**不会拦截、改写
或减速**仍配置为“X 拉黑”的即时动作；这些动作继续走原项目的前台队列。即时拉黑
如果失败，失败目标可以进入延迟队列，但这不等于即时模式本身被延迟执行。

功能关闭时，本地隐藏仍按原项目逻辑工作；只是延迟队列不再发送 X 请求。

## 动作分流

新记录通过结构化字段保存“请求动作、实际动作和延迟资格”，避免依赖展示文字判断。

| 记录或原动作 | 延迟拉黑处理 | 原因 |
|---|---|---|
| 仅标记 | 不入队 | 没有隐藏或拉黑意图 |
| 明确选择本地隐藏 | 入队 | 推荐的两阶段路径 |
| X 静音 | 跳过 | 不改变用户原本选择，不升级为拉黑 |
| X 拉黑成功 | 记录成功并去重 | 已经达到跨设备效果 |
| X 拉黑临时失败 | 加入延迟队列 | 后续按统一限速重试 |
| X 拉黑返回 404 | 目标不可用 | 不重试，也不改用 handle |
| 被 `autoTierMode="hide"` 安全封顶为本地隐藏 | 跳过 | 不绕过上游的安全封顶策略 |
| 设置页“恢复显示”后删除的记录 | 不再处理 | 队列发送前重新检查记录是否仍存在 |

### 历史记录

旧记录没有可靠的结构化响应状态，采用以下迁移规则：

- 明确写明“静音”的记录排除；
- 其余具有数字 userId 或合法 handle 的记录默认加入；
- 理由中写着“自动拉黑”也不能直接算成功，因为旧版可能在 X 响应前就保存了该文字；
- 旧版 `origin=legacy`、`status=succeeded`、`attempts=0` 的未验证成功标记重新排队；
- 真正收到 X 成功响应后才写入可用于去重的成功状态。

该策略优先避免漏处理，因此极少数已经在 X 端拉黑、但本地没有可靠成功证据的账号
可能被重复提交一次。不调用额外查询接口时无法完全消除这种可能。

队列以 `xss:blocklist:v2` 处理记录为候选来源。只有 `xss:blocked` ID、却没有对应
处理记录或 handle 的孤立数据不能自动补全目标身份。

## 目标身份

- 有数字 userId 时使用不可变的 `user_id`；
- 缺少数字 ID 时才使用规范化并校验过的 `screen_name`；
- handle 只接受 1～15 位字母、数字和下划线；
- X handle 不区分大小写，本地使用小写键去重；
- 同一 handle 后续获得数字 ID 时切换到数字 ID；
- 如果 handle 目标已确认成功，数字 ID 状态继承该成功结果，避免重复请求；
- 数字 ID 请求返回 404 后不会再尝试 handle。

handle 可能改名，也可能被其他账号重新使用。只有 handle 的旧记录只能指向该 handle
的当前持有者，不能保证仍是当初隐藏的账号。额外查询 X 接口也只能解析当前持有者，
不能恢复历史身份，因此第一版不增加拉黑前查询。

## 权限与账号绑定

开启开关时，扩展检查 `x.com` / `twitter.com` 可选网站权限：

- 已有权限时不重复申请；
- 权限缺失时由 Chrome 显示授权请求；
- 用户拒绝时开关保持关闭；
- 复用原项目 X 静音/拉黑的 `ensureXPermission()`，不是 OAuth 授权。

请求直接由当前 X 页面发送到 X，不经过项目服务器。扩展不会保存 X 密码、Cookie
或 CSRF Token。

开启时还会保存最近从 X 页面识别到的当前账号 handle。每次发送前再次校验：

- 未登录或无法识别账号：暂停；
- 当前 handle 与绑定账号不一致：暂停；
- 账号一致：允许调度器继续。

这个绑定不是 X 接口要求，而是防止持久队列在切换 X 账号后被错误账号执行。需要
换号时，先关闭开关，在目标账号的 X 页面刷新一次，再回设置页重新开启。

## 调度、限速和并发

- 始终一次一个，不并发；
- 两次延迟队列尝试随机间隔 45～75 秒，均值约 60 秒；
- 滚动一小时最多 60 次；
- 滚动 24 小时最多 360 次；
- 所有实际 POST 尝试都计数，包括失败和 404；
- 多个 X 标签页通过 Web Locks 共用一个调度器；
- 每次发送前再次检查开关、账号、记录、限额和熔断状态；
- 页面关闭、浏览器退出或电脑休眠时暂停，下次打开匹配账号的 X 页面后继续。

“60/小时”是短时上限，不代表可以全天持续 60/小时。由于还有 360/滚动 24 小时
上限，连续运行最多约六小时后就会等待旧请求移出 24 小时窗口。实际速度还会受到
页面状态、浏览器休眠、X 动作自身节流和重试退避影响。

这些限制只约束延迟队列。原项目即时 X 静音/拉黑仍使用自己的、更快的前台限速。

## 错误处理和状态展示

| 结果 | 本地状态 | 后续行为 |
|---|---|---|
| X 成功响应 | 已 X 拉黑 | 保存成功时间，后续去重 |
| HTTP 404 | 目标不存在/不可用 | 终态，不重试、不使用 handle 回退 |
| HTTP 401/403 | 等待重试并停止调度器 | 需要关闭再重新开启，以重新确认登录和权限 |
| HTTP 429 | 限流冷却 | 至少一小时，并采用更长的 `Retry-After` |
| 网络错误、408、425、5xx | 等待重试 | 最多三次，退避 5 / 15 分钟 |
| 其他客户端错误 | X 拉黑失败 | 终态，不无限重试 |
| 页面在请求中断开 | 重新待处理 | 下次页面加载时恢复 |

已有的 404 失败记录会自动迁移为“目标不存在/不可用”。同一目标之后再次被本地
隐藏也不会重新入队。404 不计入“失败”，但请求已经真实发送，所以仍保留在 24 小时
请求计数中。

设置页汇总显示：待处理、已拉黑、失败、目标不可用、handle 兜底和 24 小时请求数。
处理记录逐条显示待处理、处理中、等待重试、成功、失败或跳过原因；悬停状态标签可
查看 HTTP 状态、尝试次数和 handle 执行方式。实现细节“handle”不在每条可见标签中
重复显示。

## 本地存储、去重和数据丢失

| 键 | 用途 |
|---|---|
| `xss:blocked` | 本地隐藏快速 ID 集合 |
| `xss:blocklist:v2` | 处理记录、目标资料和结构化动作 |
| `xss:delayed-block:states:v2` | 数字 ID / handle 队列、重试和成功状态 |
| `xss:delayed-block:meta:v1` | 请求时间戳、暂停原因和下次运行时间 |
| `xss:settings` | 延迟开关、绑定 handle 和其他设置 |

旧的 `xss:delayed-block:states:v1` 数字 ID 状态会在首次队列写入时迁移到 v2。

本地成功状态是避免重复请求的主要依据。第一版不在每次拉黑前读取 X 服务端拉黑列表，
因为那会增加请求、增加接口依赖，而且不能解决旧 handle 身份变化问题。

卸载扩展、清除扩展数据或删除 Chrome 配置会丢失本地记录和去重状态，但不会解除 X
服务端已经完成的拉黑。状态丢失后，历史记录重新导入可能导致少量重复请求。成功响应
和本地写入之间如果恰好发生页面崩溃，也可能再尝试一次，因此不保证 exactly-once。

设置页“恢复显示”只删除本地隐藏和处理记录，不会自动解除 X 端静音或拉黑。

## 数据迁移

商店版和侧载版存储互不相通。本功能不增加图形化导入器；手动导出、合并、核对和
隐私注意事项见 [商店版数据迁移](./DELAYED-AUTO-BLOCK-MIGRATION.md)。

## 实现位置与验证

| 文件 | 职责 |
|---|---|
| `extension/lib/delayed-block.ts` | 目标身份、状态迁移、队列、限速、重试和统计 |
| `extension/entrypoints/content.ts` | X 页面调度器、账号校验和最终发送前安全检查 |
| `extension/lib/x-action.ts` | 复用现有 X 动作请求、跨标签页节流和可取消检查 |
| `extension/entrypoints/options/App.tsx` | 开关、汇总统计和逐条状态展示 |
| `extension/lib/store.ts` | 处理记录的结构化动作字段 |

不使用真实 X 账号的本地验证命令：

```bash
cd extension
npm run compile
npm test
npm run build
```

自动化测试覆盖动作分流、历史状态迁移、数字 ID/handle 切换、去重、限速、熔断、
404 终态以及发送前取消。真实 X 接口可能变化，生产请求只能由使用者自行少量验证。
